# 07-维护与文档同步约定

> 本约定是硬性要求：**任何对代码、数据库、配置、权限数据的修改，都必须同步更新对应文档**，
> 否则视为未完成。

## 1. 修改触发文档同步的场景

| 修改类型 | 必须同步的位置 |
| ---- | ---- |
| 新增/修改/删除后端接口 | 05-接口与权限标识对照表 + 02 设计文档 + 06 测试报告 |
| 新增/修改权限标识(permission_key) | 03 数据库变更脚本 + 05 对照表 + 前端 v-perm/路由表 |
| 数据库结构或种子变更 | 03 变更清单 + db/changelog 新脚本 + 06 复测 |
| 前端页面/按钮/权限逻辑 | 05 对照表 + 02 设计文档 + **12 页面与界面说明（重拍截图）** + README |
| 配置项(yml)变化 | 02 设计文档 + 04 部署手册 |
| 默认账号/初始数据变化 | 03 数据库说明 + 04 部署手册 |

**配图同步**：`12-页面与界面说明` 的全部截图由 `tests/capture-screenshots.cjs` 生成，
只要页面的**布局、文案、控件、按钮可见性**发生变化，就必须重拍并提交（命名固定，覆盖即可）。
提交前建议执行 `node tests/check-doc-images.cjs`，确认文档中的图片与相对链接均有效。

**界面改动的客观门槛**（主观观感由人评审，可用性由脚本判定，先过脚本再提交）：

| 脚本 | 判定内容 |
| ---- | ---- |
| 
pm run lint（两端前端） | ESLint 静态检查：未使用变量、模板结构等问题（CI 中执行，0 warning 门槛） |
| `tests/check-tokens.cjs` | token 引用是否都已定义；单端独有 token 是否登记理由；两端同名字面值是否一致；**阴影类 token 是否整值使用**（拼接会让整条声明失效） |
| `tests/check-design-a11y.cjs` | 对比度（WCAG 2.1，正文 ≥4.5:1 / 次要 ≥3:1）；1280·1440·1920 与 360·390·430 三档宽度无溢出；触摸目标 ≥44px；占位符实测对比度 |
| `tests/check-permission-doc-consistency.cjs` | 《05》接口行与后端 `@PreAuthorize` 注解是否一一对应 |
| `tests/gen-role-endpoint-matrix.cjs --check` | 《05》第 9 节角色可访问矩阵是否为最新（种子或接口变化后需重新生成） |
| `tests/check-perm-keys.cjs` | 前端 `v-perm` / `perm:` 引用的权限标识是否都在数据库脚本中定义 |

**生成型文档**：《05》第 9 节角色可访问矩阵由 `gen-role-endpoint-matrix.cjs` 生成
（在 `BEGIN:ROLE-ENDPOINT-MATRIX` / `END:ROLE-ENDPOINT-MATRIX` 两个标记之间）。
触发重新生成的改动：新增/删除接口、修改 `@PreAuthorize`、调整角色授权种子（db/init 或 V1.0.x 脚本）。

截图脚本已做确定性处理（隐藏 dev 态浮层、截图前移开鼠标、弹层等待尺寸稳定），
因此"改动前后逐像素比对"的结果可直接作为证据：差异一定是真实界面变化。

**多步改版期间的过渡做法**：若正在进行的是一次分多步的前端改版（如 E1 token → E2 外壳 → E3 列表…），
中间步骤**不逐次重拍文档配图**（避免二进制反复覆盖），而是：
1. 每步把截图写入 `admintem-docs/design-preview/`（已在 `.gitignore` 中，仅本地评审用）；
2. 评审通过后再统一重拍一次 `admintem-docs/images/`，并在提交信息中注明"文档配图同步"；
3. 改版期间文档配图可能落后于代码，这一点需在改版收尾时明确消除（不得长期停留在过渡状态）。

## 2. 变更流程（推荐顺序）

1. 在 `db/changelog/` 新增递增版本脚本（如 V1.0.2__xxx.sql），编写完整注释；
2. 实现/修改代码（后端与前端各保留充分注释与日志）；
3. 在 `tests/api-regression-test.ps1` 中补充/调整对应断言；
4. 复跑回归（目标：0 失败），必要时执行 `tests/cleanup-test-data.sql` 恢复基线；
5. 更新文档编号文件与 README 导航；在《06-测试报告》追加本次结果；
6. 提交说明写清变更内容与影响面。

## 3. 文档版本与命名

- 文档按功能编号：`01 需求范围 / 02 系统设计 / 03 数据库 / 04 部署操作 / 05 接口权限 / 06 测试 / 07 约定`；
- SQL 脚本命名：`V<主>.<次>.<修订>__<简短英文说明>.sql`；
- 后端版本号见 `admintem-backend/pom.xml`，与脚本版本对应（如 1.0.0 ↔ V1.0.x）。

## 4. 权限新增速查（最常见的维护动作）

新增一个“按钮/操作”时按此五步，缺一不可：

1. DB：`db/changelog` 插入 type=1 记录（permission_key 全局唯一），并给目标角色授权；
2. 后端：Controller 目标方法加 `@PreAuthorize("@rbac.hasPerm('<同一key>')")`；
3. 前端：对应按钮加 `v-perm="'<同一key>'"`；
4. 文档：更新 03 变更清单 + 05 对照表；
5. 测试：回归脚本覆盖“有 key 放行 / 无 key 403”。

## 5. 回滚约定

- 代码回滚：Git 版本回退后重跑回归即可；
- 数据回滚：增量 SQL 均可按文件头注释人工反向执行；破坏性操作前先备份相关表
  （`CREATE TABLE xxx_bak AS SELECT * FROM xxx` 或导出）。

## 6. 框架代码基线备份（backup 分支 + tag）

**为什么需要**：前端视觉改版、结构性重构这类"面大且主观"的改动，一旦中途推翻，
需要有明确、可核对的还原点，而不是靠记忆逐个文件改回去。

| 对象 | 名称 | 指向 | 说明 |
| ---- | ---- | ---- | ---- |
| 备份分支 | `backup/framework-baseline-20260923` | `3009b84` | 与当时的 `master` 同一提交；**冻结，不在其上继续开发** |
| 附注标签 | `framework-baseline-20260923` | `3009b84` | 不可变快照，作为最终依据（分支可被移动，tag 不会） |

备份内容：三端（`admintem-backend` / `admintem-vue` / `admintem-mobile`）+ 全部文档，
即"登录/注册/用户/角色/权限 + 移动端首页/我的"这套框架代码的完整可运行状态
（当时验收：回归 78/78、后端单测 85/85、桌面 E2E 21、移动 E2E 41）。

**回退/取用方式**（按场景选最小动作）：

```bash
# 1) 只读查看备份状态（不要在备份分支上提交）
git checkout backup/framework-baseline-20260923

# 2) 设计改版回退：只把两个前端恢复到基线（推荐，后端与文档保持现状）
git checkout backup/framework-baseline-20260923 -- admintem-vue admintem-mobile

# 3) 取回单个文件
git checkout backup/framework-baseline-20260923 -- admintem-vue/src/layout/Layout.vue

# 4) 整仓回到基线（危险操作：会丢弃之后的所有提交，执行前先确认无未推送工作）
git reset --hard framework-baseline-20260923
```

**约定**：

1. 备份分支与标签**只读**：不提交、不合并、不删除；
2. 新的重要基线（例如设计改版完成并通过全部验收）应**另建**备份分支与标签并注明日期，
   形成可追溯的基线序列，而不是覆盖旧备份；
3. 从备份回退后必须重跑验收（回归 78 项 + 两端 E2E + 构建），并在《06-测试报告》记录。
