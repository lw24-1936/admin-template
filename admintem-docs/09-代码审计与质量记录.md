### 6.8 B7（窗口内追加）：热查询索引补齐（V1.0.4）

排查方法：把代码里的查询条件与 `information_schema.STATISTICS` 对照，发现 `role_key`、
`permission_key` 无索引，两张关联表缺少反向（按 role_id / permission_id）索引。

| 索引 | 表(列) | 支撑查询 | EXPLAIN（前 → 后） |
| ---- | ---- | ---- | ---- |
| `idx_role_key` | sys_auth_role(role_key) | 登录判定超级角色、注册取默认角色、唯一性校验、`selectByRoleKeys` | `type=ALL, possible_keys=NULL` → `type=ref, key=idx_role_key` |
| `idx_permission_key` | sys_auth_permission(permission_key) | 唯一性校验、`selectByKeys` | `type=ALL` → `type=ref, key=idx_permission_key` |
| `idx_role_id` | sys_auth_user_role(role_id) | `countByRoleId`、按角色失效缓存 | `type=ALL` → `type=ref, key=idx_role_id` |
| `idx_permission_id` | sys_auth_role_permission(permission_id) | 删除权限时级联清理关联 | `type=ALL` → `type=ref, key=idx_permission_id` |

- 保持**非唯一索引**（唯一性由应用层 `countByXxx` 保证），与既有 `idx_user_name` 约定一致，
  避免逻辑删除后同名重建被唯一键挡住；
- 脚本 `db/changelog/V1.0.4__add_hot_query_indexes.sql` 幂等（用 `COUNT(*)` 判断后动态执行 DDL），
  第二次执行输出 4 条 skip；一键初始化脚本的建表语句已同步这 4 个索引；
- 变更后复测：回归 75/75、桌面 E2E 21/21、移动 E2E 41/41，均无回退。

> 踩坑记录：写 SQL 脚本时，注释行与紧随其后的语句之间出现过**换行丢失**，
> 导致整条 `SELECT ...` 被并入注释而报语法错误；此外在动态 SQL 里放中文提示文本会被
> 客户端字符集影响解析。最终采用"正文注释用 ASCII + `mysql -e "source <file>"` 执行"的方式，
> 并通过 EXPLAIN 复核才确认索引真正生效。

## 15. D3：操作审计入库（晚间场，E 组收尾后）

**动机**（来自《10》P0 清单，也是权限系统的治理刚需）：改造前的留痕手段都无法回答
"某条权限是谁在什么时候移除的、成功了还是被拒绝"——应用日志会被清理、慢 SQL 日志不关心人、
业务表的 `update_by` 只保留最后一次。因此新增独立审计表。

| 产出 | 说明 |
| ---- | ---- |
| `db/changelog/V1.0.5__add_audit_log.sql` | 新增 `sys_auth_audit_log`（只追加、无 `is_deleted`、4 个审计查法索引）；一键初始化脚本同步 |
| `aspect/AuditLog.java` + `AuditLogAspect.java` | 注解式审计切面；`finally` 中记录，成功/业务失败/抛异常都留痕 |
| `aspect/AuditLogFactory.java` / `AuditTargetResolver.java` | 审计记录构造与目标解析集中一处，避免字段口径漂移（也便于单测） |
| `service/AuditLogService(.Impl)` | 只追加写库；失败不外抛、入库前按列宽截断 |
| 控制器注解 | 登录/注册/登出/改本人资料与密码 + 用户 5 项 + 角色 4 项 + 权限 3 项，共 17 个动作 |
| 两处 403 出口 | `GlobalExceptionHandler`（方法级）与 `RestAccessDeniedHandler`（过滤器链）记录 `ACCESS_DENIED` |

**关键设计判断（逐条都有理由）**

1. **越权也要留痕**：`@PreAuthorize` 在方法调用前就拒绝，业务方法从未执行、注解切面看不到这次请求；
   而"谁尝试了无权操作"恰是审计最有价值的信号，故在两处 403 出口单独记录；
2. **审计失败绝不影响业务**：把异常吸收放在最靠近持久化的一层（服务实现），
   并显式写了"审计服务抛异常时业务仍正常返回"的断言——审计是附加动作，不能反过来成为故障源；
3. **开关只有一处判断**：放在持久化边界，避免"切面关了但 403 出口还在写"的半开状态；
4. **不做自动清理**：审计属合规留痕，删除应由运维显式执行（《04》提供清理 SQL），
   程序自动删会"悄悄丢失审计证据"；
5. **不新增接口与权限标识**：本期只落库，查询用 SQL（面向审计而非面向业务用户），
   查询页面/接口列入《10》扩展规划——这样对既有 78 项回归、两端 E2E、权限对照表零影响。

**实测（真实请求驱动，非构造数据）**：应用 V1.0.5 后重启服务，手工登录 1 次 + 完整跑接口回归，
库内得到 **51 条审计记录、51 个不同 traceId**；覆盖 13 类成功动作、7 条业务失败
（501/505/509）与 **6 次越权尝试**（`ACCESS_DENIED`，含 user/role/permission 三类接口）。
字段抽样与分布表见《06》第 4.2 节。

**单测**：新增 24 项（`AuditLogFactoryTest` 8、`AuditTargetResolverTest` 7、
`AuditLogServiceImplTest` 6、`AuditLogAspectTest` 3），后端单测由 85 → **109 项全通过**。
其中解析器测试暴露了一处真实口径问题：登录请求体字段是 `username`（小写 n），
而用户/权限 DTO 是 `userName`；反射按大小写精确匹配，少列一个 getter 就会出现
"登录审计没有操作人"的静默缺失——已补 `getUsername` 并用测试钉住。

**过程中的两处发现（都值得记录）**

1. **生成器把注释当成了数据**：初始化脚本在 `INSERT ... VALUES` 的多行之间插入了中文说明

2. **首个字段误用类级 javadoc**：批量补注解时，首个字段的说明被错误地取成了类的说明

   遇到类/接口声明或另一段 javadoc 即中止。**教训：凡"向上找最近注释"的逻辑，
   都必须显式设定终止条件**，否则会跨过类边界取值。

## 17. D4：登录风控增强（IP 维度 + 告警日志）

**背景**：原有防爆破只做**账号维度**——连续失败 5 次锁账号。它能挡住"盯着一个账号猜密码"，
但挡不住**撞库**：攻击者在同一来源不断更换账号名，每个账号都只失败一两次，账号维度永远不会触发。

| 产出 | 说明 |
| ---- | ---- |
| `security/LoginRiskGuard`（新增） | 把账号维度与 IP 维度的风控策略抽成独立组件：阈值、时长、key 前缀、告警文案集中一处；登录主流程只保留"检查 → 认证 → 记失败/清失败"三步意图 |
| `util/web/ClientIpUtils`（新增） | IP 解析单一出处（X-Forwarded-For 首跳 → X-Real-IP → remoteAddr）；审计留痕改为复用同一实现 |
| `ResultCode.LOGIN_IP_LIMITED(511)` | 与账号锁定（502）区分：前者是"这个来源网络被限"，后者是"这个账号被锁"，前端提示与运维告警口径不同 |
| 配置项 | `admintem.auth.ip-limit-enabled`（**默认 false**）、`ip-max-login-fail-count`（20）、`ip-lock-minutes`（10）与两个 key 前缀 |
| 告警日志 | 触发限制与限制期内被拒均输出带 `[登录风控]` 前缀的 WARN（只记账号与 IP，绝不记密码） |

**设计取舍（都写进了《02》3.4 与配置注释）**

1. **默认关闭**：本地联调与演示常在同一 IP 上反复输错密码，开启会挡住开发者；
   生产建议开启，并在《04》给出"误封后如何立即解封"的运维命令；
2. **不牵连账号**：IP 维度只惩罚来源——实测中限制期内提交正确密码依旧被拒，这既是设计意图也是验证证据；
3. **识别不到 IP 就不拦**：取不到来源时宁可不做该维度，避免误伤；
4. **成功登录不解封**：只清失败计数；已进入限制期的来源必须等待到期；
5. **口径统一**：风控与审计共用 `ClientIpUtils`，避免"审计的 IP 与风控的 IP 对不上"。

**实测**（临时以阈值 3 次启动）：错误密码 ×3 → 501；第 4 次 → **511**；限制期内正确密码 → **511**；
应用日志出现两条 `[登录风控]` WARN；Redis 出现 `admintem:auth:lock:ip:127.0.0.1`。
随后清理风控键、以默认配置重启，复跑接口回归 78/78 与两端 E2E 全通过（默认关闭时行为与改造前一致）。

**单测**：新增 `LoginRiskGuardTest` 7 项（阈值锁定、默认关闭不计数、只惩罚来源、
IP 缺失时跳过、成功登录清理但不解封等），后端单测 109 → **116 项全通过**。

**测试过程中的一处"测试说谎"风险（值得记录）**：首版 Mock 里用 `bucket.delete()` 只清理
"锁定标记"集合，而真实 Redis 的 `DEL` 与类型无关；这条不忠实的模拟先让一个用例失败，
排查后确认是 Mock 语义问题而非产品缺陷。处置有两步：① 把测试替身改为"删除键时两类状态都清"，
与真实行为对齐；② 顺手把产品代码里清理计数键的写法从 `getBucket(...).delete()`
改为 `getAtomicLong(...).delete()`，让"用什么类型存就用什么类型删"在代码上显式可见。
——**教训：测试替身与真实行为不一致时，失败信息会指向错误的方向；替身要模拟语义，而不只是模拟方法。**

## 18. 代码审查驱动的加固（B1：唯一性、缓存时机、契约、停机、密钥缓存）

**缘起**：以"高级开发工程师视角"对项目做了一轮通读（后端 125 文件 / 9173 行、桌面端 38 文件 /
4332 行、移动端 19 文件 / 1509 行、文档 13 篇），结论是主体质量不错（无 `SELECT *`、
无 N+1、SQL 全在 XML、116 项单测），但仍有若干"平时不发作、并发或发布时会咬人"的点。
本节记录 B1 一批的修复与判断依据。

### 18.1 唯一性从"应用层约定"变成"数据库约束"

- **问题**：`user_name`/`role_key`/`permission_key` 只有普通索引，唯一性靠 Service 里
  "先 count 再 insert"。两个并发请求可以同时通过校验并双双插入，表里出现同名账号；
  登录 `selectByUserName` 走 `LIMIT 1`，身份随机落到其中一行，权限随之错乱。
- **修法**：`V1.0.6` 增加三个**函数唯一索引** `((IF(is_deleted = 0, 业务键, NULL)))`。
  逻辑删除行表达式为 `NULL`，MySQL 唯一索引允许多个 `NULL`，因此"未删除行唯一 +
  删除后可同名重建"同时成立（普通唯一索引做不到后者）。
- **配套**：`insert` 的 `DuplicateKeyException` 转成与串行一致的业务码（505 / 400+具体提示），
  让并发与串行两条路径对外表现一致——否则同一件事会因为"赶上并发"而报不同的错。
- **实测**：直接插第二个 `admin` 被拒（1062）；插两条 `is_deleted=1` 的 `admin` 允许；
  API 层重复创建返回 505。

### 18.2 缓存失效从"提交前"挪到"提交后"

- **问题**：`evictUser/evictUsers` 写在 `@Transactional` 方法体内，即提交前。
  并发读会在"已删除缓存、尚未提交"的窗口回源读到旧数据并写回快照（TTL 30 分钟），
  于是最坏 30 分钟内按钮权限是错的。
- **修法**：新增 `support/AfterCommitExecutor`，把缓存失效与令牌吊销统一挂到 `afterCommit`；
  无事务时立即执行（既有语义与单测不受影响）；回调异常只告警不外抛（缓存由 TTL 兜底）。
- **验证**：`AfterCommitExecutorTest` 4 项，显式断言"注册阶段不执行、提交后执行、回滚不执行、
  异常不外抛"。

### 18.3 响应体契约与实现对齐

- **问题**：`Result.isSuccess()` 是 getter，Jackson 把它序列化成 `success`，
  真实报文是 `{code,message,data,success}`，而《05》约定的是三字段。
- **修法**：`@JsonIgnore` + `ResultTest` 钉住契约（成功/失败各一条断言）。

### 18.4 优雅停机

- 补 `server.shutdown=graceful` 与 `spring.lifecycle.timeout-per-shutdown-phase=30s`：
  没有它时发布/重启会把正在执行的登录、审计写入等请求直接切断。

### 18.5 签名密钥缓存

- `signingKey()` 原先每次调用都重建（每个已登录请求都会走一次 `parseToken`），
  改为构造时算一次存字段；JWT 密钥运行期不变，缓存安全。

### 18.6 一次真实事故：初始化脚本清空了审计表（必须记录）

**经过**：为验证一键初始化脚本的建表语法，我把脚本复制到临时文件、只把外层 `-e` 的默认库
换成临时库后执行。但脚本内部有一句 `USE \`admintem_new\``，它把会话切回了线上库，
于是整套 `DROP TABLE` + `CREATE TABLE` 在**线上库**执行：表结构重建、种子数据回到基线，
审计表里 180 条验证历史被清空。

**影响**：功能与数据基线无损（用户 2 / 角色 3 / 权限 18 / 关联 24+3 与基线完全一致，
密码散列未变、登录正常）；损失的是审计表里我们自己做回归留下的历史记录。

**根因（两层）**：
1. 我的校验方法错了——用**破坏性脚本**去验证语法，本应复制脚本并改掉其中的库名；
2. 脚本本身也有设计缺陷——"危险动作 + 无声默认"：`USE` 让脚本在任何会话里都指向线上库，
   且没有任何确认环节。

**修复**：
1. 脚本加入安全闸门：未执行 `SET @admintem_confirm_reset = 1` 时用 `SIGNAL` 中止，
   不删除任何表（实测：未确认建表数 0；确认后 6 表 + 3 索引）；
2. 《04》写明两条执行方式与"在共享库校验语法必须改写库名"的注意事项；
3. 事故与教训写入本节，作为流程约束。

**教训**：**对"会删数据"的脚本，验证方式本身也要当作生产操作来设计**；

## 20. B2：Redis 往返、批量失效、Actuator 与审计异步

### 20.1 每请求 2 次 Redis 往返 → 1 次

认证过滤器要两样东西：令牌白名单（判吊销）与用户快照（判权限），原先是两次 `GET`。
改为一次 `RBuckets.get(tokenKey, permKey)`（底层 MGET）：

- RTT 减半（QPS 100 时每分钟少约 6000 次往返）；
- 两次读取原子化，不会出现"新白名单 + 旧快照"的中间态；
- `JwtTokenService.checkRedisToken` 随之删除（避免同一语义存在两个实现）。

批量失效同样从"逐个 DEL"改为 `RKeys.delete(keys...)`：改一个权限可能影响成百上千用户，
逐个删除会把一次操作放大成 N 次往返。这两点都用单测钉住（`verify(times(1))`），
防止后续重构悄悄退化。

### 20.2 Actuator：只开 health/info

生产最需要的是"服务活着吗、DB/Redis 通吗"，而不是把 env/beans/heapdump 暴露出去。
故 `management.endpoints.web.exposure.include: health,info`、`show-details: never`，
白名单只放行 `/actuator/health`（含 liveness/readiness）。

实测：`/actuator/health` 200 `{"status":"UP","groups":["liveness","readiness"]}`；
`/actuator/env` 返回 401（未暴露且未放行）。

### 20.3 审计异步化：不丢是第一位

独立线程池（1 线程 / 队列 2000 / **CallerRunsPolicy** / 停机等待 10s）：

- 业务不再等待审计落库；
- 队列满时由调用线程执行——"宁可这一次慢一点，也不能丢审计"；
- MDC 通过 `TaskDecorator` 传递，审计日志与接口日志、SQL 日志共用 traceId；
- **只异步"落库"**：审计对象的构造仍在请求线程（需要 `HttpServletRequest` 与登录上下文）。

一个容易忽略的细节：`@Async` 靠代理生效，类内自调用不会异步。
因此把 `recordAsync` 放在接口上、由切面/处理器从外部调用，
并保留同步 `record` 供测试与 CallerRuns 路径使用。

### 20.4 验证

单测 122 → **129 项全通过**；接口回归 78/78；实测审计记录 2 秒内可见；
`/actuator/health` 200、`/actuator/env` 401；探针权限已清理，权限基线回到 18 条。

### 21.1 CI：把"手工门槛"变成流水线

4. `clean-disabled=true`、`placeholder-replacement=false`。

## 22. B4：构建、Swagger 授权、密码策略与 URL 状态

### 22.1 前端构建：把"包太大"的告警真的打开

三处调整：

1. `vue-devtools` 只在 `command === 'serve'` 时加载：它是调试工具，不该进用户浏览器；
2. vendor 拆分（Vite 8 底层 Rolldown **只接受函数形式** `manualChunks`，对象形式会报
   "manualChunks is not a function"）：`vendor-element` 337KB + CSS 177KB、`vendor` 195KB、
   `vendor-vue` 28KB，业务 chunk 回落到 9–13KB；
3. `chunkSizeWarningLimit` 从 1500 恢复到 500——此前等于把告警关掉了。

收益不在"首屏更快"（总量没变），而在**缓存命中**：改业务代码时用户无需重新下载框架与组件库。

### 22.2 Swagger 出现 Authorize

本项目用自定义头 `admintem_token: "LAUNCH <jwt>"`，不是标准 Bearer。补上安全方案后，
Swagger UI 会出现 Authorize 按钮，填入 `LAUNCH <token>` 即可调受保护接口。
踩过一个坑：`io.swagger.v3.oas.models.security.SecurityScheme` **没有 `paramName()`**，
APIKEY 的"参数名"就是 `name` 字段（我一开始写了 `paramName` 导致编译失败）。

### 22.3 密码策略：强度可配 + 登录时静默升级

- `PasswordPolicy` 统一编码强度、复杂度校验、`needsRehash` 判定；
- 登录成功后按需重编码落库（明文只在登录这一刻可得）；
- 复杂度默认关闭，开启后**四条路径**（注册/新增/改密/重置）都校验——
  只覆盖注册会留下"管理员重置密码"这个后门；
- 生产（profile 含 pro）若仍用示例 JWT 密钥，启动直接失败（实测报错信息可读）。

### 22.4 一个被新功能暴露的既有 bug：动态路由重放丢 query

做"列表筛选写回 URL"时发现：深链 `?pageNum=2&userName=admin` 打开后条件没了。
根因在守卫里——

```js
// 修复前
return { path: to.fullPath, replace: true }   // fullPath 含 ?a=1，但 path 不承载 query
// 修复后
return { path: to.path, query: to.query, hash: to.hash, replace: true }
```

`to.fullPath` 是"路径 + 查询 + 哈希"的拼接串，把它塞进 `path` 会让 query 在重放时丢失。
这是**既有缺陷**（不是本次引入），只是此前没有"带查询参数的深链"场景去触发它。
修复后实测：落地 URL 保留参数、账号输入框回填 `admin`、页码为 2。

> 教训：新增能力（URL 同步）常常会照亮旧代码里的隐性缺陷；发现时按"既有 bug"单独说明，
> 不要混进新功能的功劳里，也不要因为"不是我的锅"就绕过。

### 22.5 URL 状态同步的实现取舍

`composables/useQuerySync.js` 只做**单向**同步（query → URL）+ 首屏水合：

- 不做 URL → query 的反向监听，避免"写 URL → 路由变化 → 再写 URL"的回环；
- 页码 1 / 每页 10 等默认值不写进地址栏，保持可读；
- 只在 query 真变化时 `router.replace`（replace 而非 push，避免"后退"变成一步一筛）。

后端单测 129 → **138 项全通过**；桌面 E2E 21、移动 E2E 41、接口回归 78 全通过；

## 24. B5：操作审计查询（补上"只写不读"的缺口）

### 24.1 背景

审计表从 V1.0.5 起一直在写（本轮已有 285 条），但没有任何读接口，
运维要看记录只能连库跑 SQL —— 数据有、出口没有，等于能力只完成了一半。

### 24.2 后端

- `AuditLogPageQuery`：时间用**字符串**接收而不是 `LocalDateTime`，理由是前端日期控件
  给的就是 `yyyy-MM-dd HH:mm:ss`，而项目没有全局 JavaTime 格式配置；
  解析失败可以给出中文提示，而不是一个反序列化 400；
- SQL：`operator` / `action` 等值或前缀匹配 + 固定 `created_time DESC, id DESC`，
  与 V1.0.5 的三个联合索引一一对应；同毫秒也能稳定翻页（不会重复/漏行）；
- 服务层：时间解析（支持 `HH:mm:ss`、`HH:mm`、纯日期三种写法，结束时间纯日期补 `23:59:59`）、
  区间反转校验、结果转中文、时间格式化；
- 控制器：两个只读接口共用同一按钮权限 `sysAuthAuditLog:paginQuery`。

### 24.3 前端：一个"组件未注册"的坑

页面第一次跑起来时日期选择器**根本没渲染**、明细抽屉变成页面底部的裸文本。
控制台真相是：

```
[Vue warn]: Failed to resolve component: el-date-picker
[Vue warn]: Failed to resolve component: el-descriptions-item
```

本项目为了控制体积，Element Plus 是**按需注册**（`main.js` 里的 `elementComponents` 数组 +
逐个 `style/css` 导入）。新页面用到 `el-date-picker` / `el-descriptions` / `el-drawer`
却没登记，Vue 就把它们当成未知标签渲染。

**教训**：按需引入模式下，"用了新组件"必须同时做两件事——在数组里补一行、在样式区补一行；
只写模板不注册不会报错，只会静默退化。已在 `main.js` 的维护提示里强化这条。

### 24.4 前端：工具条被压扁

日期范围控件声明 360px，实际被挤成约 60px、叠在"查询"按钮上。
原因是筛选区的 flex 子项默认 `flex-shrink: 1`，空间不足时**先压缩控件**而不是换行。
在 `TableToolbar` 里加 `.table-toolbar__filters > * { flex: 0 0 auto; }`：
放不下就换行（父容器本来就有 `flex-wrap: wrap`），控件宽度不被改写。
此改动对所有列表页生效（用户/角色/权限页同样受益）。

## 25. B6：前端 ESLint 接入

### 25.1 为什么现在才加

项目一直靠"人工 review + 各页面写法互相模仿"保持一致，但这类约定拦不住
未使用变量、未定义引用、模板结构问题——它们在运行时表现为
"某个按钮点了没反应"或"变量悄悄是 undefined"，很难靠肉眼发现。

### 25.2 规则取舍：只拦真错误，不争风格

开启 `vue3-essential` + `no-unused-vars` / `no-undef` / `no-dupe-keys`，
关闭 `vue/multi-word-component-names` 这类命名偏好规则。
门槛是 `--max-warnings 0`：新增的未使用变量会让 CI 变红，但**不要求**统一引号、换行等风格
（那类规则最容易演变成"为了过 lint 而改一堆无意义代码"）。

### 25.3 存量 8 处问题（全部修掉，不是调低规则）

## 26. 功能一：在线会话与强制下线（V1.0.8）

### 26.1 为什么不建"在线会话表"

令牌白名单（`admintem:auth:jwt:*`）本身就是"谁有有效令牌"的唯一事实来源。
再建一张表会引入两处状态，还要处理"应用崩溃后表里残留脏数据"的清理。
读 Redis 的成本是 SCAN + N 次 GET，在线人数通常是个位数，足够。

### 26.2 几个刻意的边界

| 决定 | 原因 |
| ---- | ---- |
| 单次最多 200 条 | SCAN 在异常情况下可能返回大量 key，接口必须自带上限 |
| TTL ≤ 0 的 key 跳过 | 否则会把"刚好过期"显示成在线，运维据此判断会出错 |
| 只返回令牌前 8 位摘要 | 页面可能被截图/日志采集，不能把可用凭证渲染出来 |
| 当前会话禁止强踢 | 自我强踢表现为"莫名其妙掉线"，应引导用「退出登录」 |
| 踢人幂等 | 目标已不在线也返回成功，语义是"操作后该账号已无有效令牌" |

### 26.3 一个模板引号错误导致的 500

页面首次加载时报 `Failed to fetch dynamically imported module`，Vite 返回 500。
根因是模板里写了 `:title="row.current ? '当前登录会话请用"退出登录"结束' : ''"`——
属性值里嵌了**英文双引号**，把 `:title` 提前截断，SFC 编译失败。

**教训**：模板属性里要表达"引用某个按钮名"，用中文引号「」或单引号，
不要用英文双引号；这类错误在编辑器里不一定高亮，但 Vite 会直接 500，
排查时应先看"动态导入 500"对应的那个文件，而不是怀疑路由或权限。

### 26.4 验证

迁移连跑两次权限稳定 22；在线列表 2 条（admin 标记 current、角色名正确、剩余 10799s）；
踢 `test` 后其 `getUserInfo` 由 200 变 **401**；页面当前会话按钮禁用、无 JS 错误。
## 27. 功能二：头像上传（V1.0.9 之前，无表变更）

### 27.1 这是项目里第一个"文件存储"需求

之前所有数据都在 MySQL/Redis 里，头像第一次引入了外部存储，因此必须先把边界定清楚：

| 关注点 | 处理 |
| ---- | ---- |
| 存哪 | 本地目录（配置化），按月分桶；多实例时改指向共享存储，接口不变 |
| 文件名叫什么 | 服务端 UUID 生成，**完全不用客户端文件名**（路径穿越与时序冲突一起解决） |
| 怎么防伪装 | 不只看扩展名，读前 12 字节做魔数校验（PNG/JPEG/GIF/WEBP） |
| 大小限制 | 配置 + Spring multipart 双闸门（超过直接在框架层 413） |
| 怎么访问 | 静态资源映射 `/uploads/avatar/**`，公开可读；明确禁止放敏感文件 |
| 换域名怎么办 | 库里只存相对路径，前端按 `VITE_API_BASE_URL` 拼 |
| 旧头像文件 | 暂不删除（换来的是"换头像后可回溯"）；如需清理，按目录做定时任务 |

### 27.2 一次由"测试工具"引起的误判

第一次用 PowerShell 的 `Invoke-WebRequest -Form` 测试上传，报"找不到参数 Form"——
当前 PowerShell 版本不支持该参数，导致请求根本没发出去，随后静态访问拿到 401
（因为 URL 是空串，实际请求打到了根路径）。换成 `curl.exe -F` 后一次通过。

**教训**：接口自测失败时先确认"请求真的发出去了"（打印状态码/原始响应），
否则会把工具限制误判成接口缺陷。

### 27.3 验证

上传 200 + 相对路径；静态访问 200 `image/png`（免令牌）；伪 PNG 被 400 拒绝；
库与 `getUserInfo` 均能读到 avatar；前端顶部头像与资料弹窗均正常、无 JS 错误。
## 28. 功能三：部门与用户归属（V1.0.9）

### 28.1 先把边界说清楚

"加个部门"听起来简单，但很容易滑向"数据权限"（按部门过滤业务数据）。
本期只做**组织归属**：部门树 + 用户挂部门 + 列表展示，不参与任何授权判定。
这条边界写进了《02》3.3.3 与《03》V1.0.9，避免后续被误用。

### 28.2 几个实现取舍

| 决定 | 原因 |
| ---- | ---- |
| 单表 `parent_id` + 内存建树 | 层级 ≤5 层，全量查询后组树最简单，也天然避免递归查库的 N+1 |
| 建树只从 `parent_id=0` 开始 | 环上的脏数据会变成"不可达"而不是让页面无限递归 |
| 上级校验沿 parentId 向上回溯（50 层护栏） | 既能阻止"移到自己的下级"，也能防脏数据死循环 |
| 删除前查子部门 + 查用户数 | 否则会出现"用户挂在不存在的部门上"，后续任何按部门统计都会错 |
| 用户列表"批量补"部门名 | 与角色一致：一次 `selectByIds`，不给主查询加 JOIN |
| 部门名做函数唯一索引 | 沿用 V1.0.6 的思路：未删除行唯一、删除后可同名重建 |

### 28.3 数据库变更的幂等写法

`dept_id` 列用 `information_schema.columns` 判断后再 `PREPARE/EXECUTE`，
其余（建表、权限、种子）都是 `IF NOT EXISTS` / `WHERE NOT EXISTS`。
实测连跑两次：部门仍 3 行、权限仍 26 条、列不重复添加。

### 28.4 一键初始化的联动

`init` 脚本同步了：`dept_id` 列与索引、`sys_dept` 建表、3 个演示部门、
权限 23–26 与管理员授权、两个演示用户的归属。
**在临时库上完整跑过一遍**（3 部门 / 26 权限 / 26 授权 / 2 用户有部门），跑完即删库。

### 28.5 验证

部门树人数正确；用户列表显示部门；删除有子部门的节点被 508 拒绝；
非法电话被 400 拒绝；前端部门页与用户页均无 JS 错误；lint 与构建通过。

### 29.2 两个必须记住的操作细节

**① Flyway 校验和会因改名而失效。**

让 Flyway 以 `baseline-from-init-script` 重新登记，9 个迁移全部重新执行成功

并在注释里写明"这是测试环境的冷启动问题，不是应用缺陷"。

## 30. 视觉升级 V2：从「纸面极简」到「层叠纸面」

### 30.1 为什么改

旧版不是"丑"，而是**层次平**：纸面 #f5f6f8 与白卡只差一点灰、按钮与链接权重接近、
每页都从一张几乎无边的卡片开始，用户没有"从哪里看起"的落点。
V2 只解决层次问题，不换主题（仍然浅色），也不引入新组件库。

参考取用（详见《02》12.6.1）：
`ui-ux-pro-max` 的浅色 slate 色板与检查清单；shadcn/ui 的**语义令牌结构**（不引入 React）；
Magic UI 的指针柔光 / blur-fade / 数字滚动（不引入 React 与 Tailwind）；anime.js v4 编排动效。

### 30.2 三层改动

| 层 | 改动 | 影响面 |
| ---- | ---- | ---- |
| 令牌 | slate 中性色、主色 #1e3a6e、三层投影、两套渐变、系统 UI 字体栈、`--lc-ring` | 全站（两端） |
| 组件 | 主按钮渐变+上浮、表格表头/行高/行入场、卡片悬停、玻璃弹层、胶囊标签、分页当前页 | 所有列表页与弹层 |
| 页面 | 外壳（侧栏/顶栏/路由过渡）、登录/注册（渐变画布 + 玻璃卡 + 指针柔光）、工作台（指标卡 + count-up + 快捷入口）、移动端三页 | 11 个桌面视图 + 4 个移动视图 |

### 30.3 三个必须记住的取舍

**① 玻璃卡不能叠 `filter` 动画。**
给登录卡加入场 `filter: blur(6px) → 0` 后，`backdrop-filter` 会失效（Chromium 下 filter 会
创建新的包含块并让 backdrop-filter 不再采样背景）。现象是"玻璃突然变成半透明白"。
处理：blur 只作用在文案层，卡片保持纯 opacity/transform。

**② 表格列宽要按"最窄可用宽度"配，不然 fixed 操作列会压盖数据列。**
用户表原来 10 列合计约 1450px，容器只有 1146px：表格内部横向滚动，
`fixed="right"` 的操作列直接盖住"角色"列，看起来像渲染错乱。
处理：去掉列表里的"性别/创建时间"（编辑弹窗与审计页仍可见），操作列 250px，
实测 `scrollWidth === clientWidth`。**判据是数字，不是肉眼**。

**③ E2E 的"标题不对"多半是基址串了。**
移动 E2E 原先读 `E2E_BASE_URL`，而桌面 E2E 也用这个变量；同一次脚本里先后跑两端，
移动端会打到桌面端口，报"标题不是移动端登录"，随后 fill 超时——看起来像页面坏了。
处理：移动脚本改为 `MOBILE_BASE_URL || E2E_BASE_URL || 5174`，并在注释里写明原因。

### 30.4 动效的可访问性

- 所有 anime 调用前先判断 `prefers-reduced-motion`，命中就直接渲染最终态；
- CSS 层还有全局 `animation-duration: 0.01ms` 兜底（两端都保留）；
- 首屏文本不预先 `opacity: 0`，动画从已渲染内容开始 —— 即使 JS 抛错，用户也能读到完整页面；
- 指针柔光只写 CSS 变量并用 rAF 合并事件，触摸设备（`hover: none`）直接不挂监听。

触摸目标 ≥44px；token 检查、双端构建、lint、桌面 E2E 21、移动 E2E 41 全通过；
21 张文档截图按新视觉重采。
