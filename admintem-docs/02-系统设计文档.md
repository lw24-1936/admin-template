## 3. 认证与令牌设计

### 3.1 登录流程

1. `POST /auth/login`（免登录白名单）提交 `{username,password,rememberMe}`；
2. 前置检查 Redis 锁定键（连续失败 5 次锁定 10 分钟，配置可调）；
3. `AuthenticationManager` 走 DaoAuthenticationProvider：UserDetailsService 查库
   （逻辑删除自动过滤、禁用抛 DisabledException），BCrypt 比对密码；
4. 成功后：清失败计数 → 组装 `LoginUser` 会话快照（角色 role_key + 权限 permission_key
   集合）写入 Redis（`admintem:auth:user:perm:{userId}`，TTL 30min）→ 签发 JWT 并写入
   白名单（`admintem:auth:jwt:{userName}`，TTL=令牌有效期）→ 返回 `{token,user}`。

> 会话构建（返回体中的 user/menus/permissions）**复用刚认证得到的快照**：
> 按 `roleKeys` / `permissionKeys` 各查一次明细即可装配角色与菜单，
> 不再重复查询角色关联与权限表。实测 SQL 条数：登录 8 条、
> `/auth/getUserInfo` 3 条（详见《09》6.7 节）。

### 3.2 JWT

- HS256，密钥、有效期可配置（`admintem.jwt.*`）；
- 载荷仅含 `subject=userName`、`userId`、`remember`、`iat/exp`（保持头部体积小）；
- 每次请求过滤器校验：验签 → 与 Redis 白名单一致 → 由缓存（或回源数据库）恢复
  `LoginUser` → 写入 SecurityContext。

### 3.3 令牌失效策略（服务端可控）

| 场景 | 处理 |
| ---- | ---- |
| 登出 | 删除白名单 + 用户快照 |
| 修改密码 / 管理员重置密码 | 删除白名单 + 用户快照（强制重新登录） |
| 禁用 / 删除用户 | 删除白名单 + 用户快照 |
| 同一账号再次登录 | 覆盖白名单（**单账号单令牌**，与旧项目语义一致，文档化） |

### 3.3.1 密码存储策略

| 项 | 设计 | 理由 |
| ---- | ---- | ---- |
| 算法 | BCrypt（沿用旧项目散列，兼容既有账号） | 自带盐、抗彩虹表；旧库密码无需重置 |
| 代价因子 | `admintem.auth.password.bcrypt-strength`（默认 10，生产可 12） | 每 +1 单次校验耗时翻倍；提高强度只影响新密码 |
| 旧散列升级 | 登录成功时若 `needsRehash` 则用当前强度重编码并落库 | 明文只在登录这一刻可得，是唯一能透明升级的时机；失败只告警、不影响登录 |
| 复杂度 | `complexity-enabled` 默认关闭；开启后注册 / 新增用户 / 改密 / 管理员重置**四条路径**都校验 | 只覆盖注册会留下"重置密码"这个后门 |
| 生产密钥 | profile 含 `pro` 且 JWT 密钥仍为示例值（含 change-me）时**启动失败** | "忘了换密钥"不会自己暴露，往往等令牌被伪造才发现 |

### 3.3.2 头像上传（本项目第一个文件存储）

用户表早有 `avatar` 字段，但一直没有上传能力。本次补上，并刻意把边界划清：

| 决策 | 原因 |
| ---- | ---- |
| 存本地目录（`admintem.upload.avatar-dir`，按月分桶 + UUID 文件名） | 部署简单，不引入对象存储依赖；多实例时指向共享存储即可 |
| 服务端生成文件名，**完全不用客户端文件名** | 杜绝路径穿越与时序冲突 |
| 三重校验：大小、扩展名白名单、**文件头魔数** | 改扩展名上传可执行文件是最常见的绕过手法 |
| 对外返回相对路径 `/uploads/avatar/...` | 换域名/换环境不用改库；前端按 `VITE_API_BASE_URL` 拼完整 URL |
| 静态目录公开可读（加入白名单） | 头像不是敏感数据；但**明确禁止**把合同/证件放这个目录 |
| 上传接口不需要权限标识 | 自服务能力（只能改自己的头像），与"修改本人资料"同级 |

> 落盘失败返回 `INTERNAL_ERROR`（对外只说"保存失败"），堆栈只进日志。

### 3.3.3 部门与组织（V1.0.9）

部门回答的是"人归属于哪里"，**不参与权限判定**。这一点必须划清，否则很容易把
组织维度误当成授权维度（那是数据权限/ABAC 的范畴，本期明确不做）。

| 项 | 设计 | 理由 |
| ---- | ---- | ---- |
| 结构 | 单表 `sys_dept` + `parent_id` 自引用 | 层级通常 ≤5 层，全量查询后内存建树最简单 |
| 用户归属 | `sys_auth_user.dept_id` 单值 | 不做多部门兼职，避免"主部门/兼岗"的复杂度 |
| 唯一性 | 未删除行 `dept_name` 唯一（函数索引） | 同名部门会让人无法在表单里区分 |
| 删除保护 | 有子部门、或部门下仍有用户 → 拒绝 | 防止出现"用户挂在不存在的部门上"的脏数据 |
| 上级校验 | 不能选自己或自己的子孙；上级必须存在且启用 | 服务端沿 parentId 向上回溯（带 50 层护栏），前端同时裁剪候选集 |
| 展示 | 部门树带 `userCount`；用户列表带 `deptName` | 运维一眼看出"这个部门几个人"，不用点进去 |

> 用户列表的部门名用"批量补"（一次 `selectByIds`）而不是 JOIN：
> 分页最多 500 行，批量补齐比给主查询加 JOIN 更简单，也不影响分页 count。

### 3.4 登录风控（账号维度 + IP 维度）

实现在 `security/LoginRiskGuard`，登录主流程只表达"检查 → 认证 → 记失败/清失败"三步意图，
策略与阈值集中在风控组件内。

| 维度 | 阈值配置 | 触发结果 | 默认 |
| ---- | ---- | ---- | ---- |
| 账号 | `admintem.auth.max-login-fail-count`（5 次） | 锁定账号 `login-lock-minutes` 分钟（业务码 **502**） | 开启 |
| 来源 IP | `admintem.auth.ip-max-login-fail-count`（20 次） | 限制该 IP `ip-lock-minutes` 分钟（业务码 **511**） | **关闭** |

设计要点：

1. **两个维度解决两类攻击**：账号维度挡住"盯着一个账号猜密码"；IP 维度挡住"撞库"
   （同一来源不断换账号名试）。因此 IP 维度只惩罚来源、不牵连账号——
   实测中限制期内即使提交**正确**密码也会被拦（511），这正是"拦来源而非拦账号"的证据；
2. **区分业务码**：502 表示"这个账号被锁"（引导用户等待），511 表示"这个来源网络被限"
   （更接近攻击特征，运维告警应区别对待）；
3. **IP 维度默认关闭**：本地联调与演示常在同一个 IP 上反复输错密码，开启会挡住开发者；
   生产建议开启（见《04》配置项表）；
4. **IP 无法识别时不启用该维度**：无法判定来源就宁可不拦，避免误伤（例如取不到 remoteAddr 的场景）；
5. **成功登录只清失败计数，不解封**：若该 IP 已进入限制期，正确密码不能提前解除限制；
6. **告警日志**：触发限制与限制期内被拒都输出带 `[登录风控]` 前缀的 WARN，
   便于日志系统按关键字抓取（日志只记账号与 IP，绝不记密码）；
7. **口径单一**：IP 解析统一走 `util/web/ClientIpUtils`（X-Forwarded-For 首跳 → X-Real-IP →
   remoteAddr），审计留痕与风控统计共用，避免"审计的 IP 与风控的 IP 对不上"。

## 4. RBAC 权限模型（本系统核心）

### 4.1 数据模型（沿用旧表）

```
sys_auth_user ──< sys_auth_user_role >── sys_auth_role
sys_auth_role ──< sys_auth_role_permission >── sys_auth_permission
```

`sys_auth_permission.type`：
- `0` 菜单：决定路由/菜单可见（含父级菜单分组）；
- `1` 按钮（操作）：决定页面内按钮与对应写接口。

`permission_key`：全局唯一权限标识，是**前端指令与后端注解共用的唯一凭据**。

### 4.2 后端判定（按钮级）

- `@PreAuthorize("@rbac.hasPerm('sysAuthUser:addSysAuthUser')")`；
- `rbac` 逻辑：登录用户拥有超级角色 `admin`（可配置）→ 放行；否则判断其
  permission_key 集合是否包含目标 key；
- 数据来源优先级：Redis 会话快照 → 未命中回源数据库并回填；
- 角色/权限变更会**主动清理受影响用户的快照**（下次请求即时生效），另有 30min TTL 兜底。

### 4.3 前端判定（按钮级 + 页面级）

- 登录/`getUserInfo` 下发 `permissions`（全部 permission_key）与 `menus`（菜单树，已过滤）；
- 按钮：`<el-button v-perm="'sysAuthUser:addSysAuthUser'">`，指令在无 key 时直接移除元素；
- 页面：路由 `meta.perm` 由守卫校验，无 key 跳 `/403`；侧边菜单按 `menus` 渲染；
- 前端隐藏仅是体验，真正安全边界在后端 `@PreAuthorize`。

**`v-perm` 的 fail-closed 语义（本轮加固）**：桌面端与移动端一致，三种情况都不渲染受控元素——
① 会话未加载完成（`permissions` 尚为空）；② 指令值为空（漏写标识，属配置遗漏，控制台报错）；
③ 用户不具备任一标识。这样"漏配"与"未加载"都不会退化成默认放行。

### 4.4 查询类接口的权限口径（约定）

- “进入页面即可查看数据”：列表/详情/下拉等**查询接口以所属菜单的 permission_key 授权**
  （如分页用户需 `userInfo:userInfo`）；
- 历史遗留按钮 `sysAuthUser:paginQuery`（“用户查询”）继续保留在数据中作展示/审计；
- 若需要“能进菜单也看不到列表”的更严格口径，把对应查询接口的注解改为按钮 key 即可（文档化扩展点）。

### 4.5 内置保护规则

| 规则 | 位置 |
| ---- | ---- |
| 不可删除/禁用内置管理员（id=1）及拥有 admin 角色的用户 | SysAuthUserService |
| 内置管理员必须保留 admin 角色（不可移除） | assignRoles |
| 不可删除、不可改 roleKey 的 admin 角色 | SysAuthRoleService |
| 删除权限级联清理其子孙与角色关联 | SysAuthPermissionService |
| 角色存在绑定用户时禁止删除 | SysAuthRoleService |

### 4.6 菜单可见性：授权 + 启用 + 展示
菜单是否出现在导航中，由三层条件叠加决定（数据语义与维护口径见《03》V1.0.3）：

| 条件 | 判定位置 | 字段/数据 | 结果 |
| ---- | ---- | ---- | ---- |
| 是否授权 | `AuthServiceImpl.buildMenus` | `sys_auth_role_permission` | 未授权不下发（admin 角色放行全部） |
| 是否启用 | 同上 | `status`（0 启用 / 1 禁用，null 按启用） | 禁用不下发 → 前端无该路由 → 直达 URL 落到 404 |
| 是否展示 | 前端 `utils/menu.js#filterVisibleMenus` | `show`（0 展示 / 1 隐藏） | 仍下发、仍注册路由（可 URL 直达），仅不在左导航/菜单清单显示 |

设计取舍：把"禁用"放在后端（安全语义，等于该页面下线），把"隐藏"放在前端
（展示语义，等同于"可达但不引导"），二者职责不重叠；隐藏页面的路由依然注册，
避免出现"数据还在但页面无法访问"的死角。

## 5. Redis 键设计（均以 admintem 前缀，与旧系统隔离）

| Key | 值 | TTL | 用途 |
| ---- | ---- | ---- | ---- |
| `admintem:auth:jwt:{userName}` | JWT | 3h / 7d(记住我) | 令牌白名单，服务端吊销 |
| `admintem:auth:user:perm:{userId}` | LoginUser JSON（不含密码） | 30min | 每请求权限判定 + 会话恢复 |
| `admintem:auth:fail:{userName}` | 失败次数 | 10min | 登录失败计数 |
| `admintem:auth:lock:{userName}` | 1 | 10min | 账号锁定 |
| `admintem:auth:fail:ip:{ip}` | 失败次数 | 10min | IP 维度失败计数（`ip-limit-enabled=true` 时才产生） |
| `admintem:auth:lock:ip:{ip}` | 1 | 10min | IP 维度限制（同上） |

### 5.1 缓存失效时机：必须在事务提交之后

用户/角色/权限变更后要清 `admintem:auth:user:perm:*`，这个动作**不能放在事务方法体内**。
否则会出现"缓存里留下旧权限"的时序：

```
线程A（更新）：删除缓存 …… 尚未提交
线程B（读）  ：缓存未命中 → 回源数据库 → 读到旧数据 → 写回缓存（TTL 30 分钟）
线程A（更新）：提交成功
⇒ 最长 30 分钟内按钮权限是错的
```

实现上统一走 `support/AfterCommitExecutor`：有事务时注册 `afterCommit` 回调，
无事务时立即执行（保持既有语义、也让单测无需改造）；回调内异常只告警不外抛
（缓存最终会由 TTL 兜底，不能让"清缓存失败"反过来影响已提交的业务）。

覆盖范围：用户增删改/重置密码/分配角色、角色增删改/分配权限、权限增删改。

### 5.1.1 在线会话与强制下线（V1.0.8）

**不新增在线表**：令牌白名单 `admintem:auth:jwt:<账号>` 就是在线事实来源。
"在线"= 持有未过期且未吊销的令牌，而不是"浏览器标签页开着"。

| 能力 | 实现 | 说明 |
| ---- | ---- | ---- |
| 列表 | SCAN `admintem:auth:jwt:*` + 逐个取 TTL | 上限 200 条（防御性，防止异常刷 key 撑爆响应）；TTL ≤ 0 的 key 直接跳过，不把已失效显示成在线 |
| 用户信息 | 一次 `selectByUserNames` + 一次关联 + 一次角色查询 | 避免逐个查造成 N+1 |
| 当前会话标记 | 用请求头里的令牌与列表值比对 | 前端据此禁用"强制下线"，避免自我强踢后莫名掉线 |
| 强制下线 | 删除白名单 key（与退出登录同一条路径） | 幂等：目标不在线也返回成功，语义是"操作后该账号已无有效令牌" |
| 令牌摘要 | 只显示前 8 位 | 便于区分同一账号的多条会话，又不会在截图/日志里泄露可用凭证 |

> 锁定状态（`admintem:auth:lock:*`）也一并展示：锁定中的账号即便持有令牌，
> 登录接口会拒绝，但已登录令牌在过期前仍可用——运营需要知道这两种状态的区别。

### 5.2 每请求只读一次 Redis（MGET 合并）

认证过滤器需要两样东西：令牌白名单（判服务端吊销）与用户快照（判权限）。
早期实现是两次 \GET\，即**每个已登录请求 2 个 RTT**。现改为
\RBuckets.get(tokenKey, permKey)\（底层 MGET）一次取回，收益：

1. RTT 减半（QPS 100 时每分钟少约 6000 次往返）；
2. 两次读取看到同一时刻的值，不存在"读到新白名单 + 旧快照"的中间态；
3. 批量失效同样改为 \RKeys.delete(keys...)\：改一个权限可能影响成百上千用户，
   逐个 DEL 会放大成 N 次往返。

> 单元测试 \RbacCacheServiceTest\ 用 \erify(times(1))\ 钉住"只有一次读取/一次批量删除"，
> 防止后续重构悄悄退化成多次往返。

## 6. 日志与慢 SQL 设计（存储参考原项目 logback.xml）

- **存储布局**（`logs/`，可用 `-DLOG_HOME` 覆盖）：

| 文件 | 内容 | 备注 |
| ---- | ---- | ---- |
| logs/admintem-backend-info.log | INFO+ 全量 | 异步写入，history/ 下按天+大小滚动 .gz，保留 30 天 |
| logs/admintem-backend-error.log | 仅 ERROR | 同上 |
| logs/sql/admintem-sql.log | 全量带参 SQL（sys-sql） | 仅 dev/test/pre；每行 = mapperId + 参数替换后 SQL |
| logs/sql/admintem-slow.log | 慢 SQL（sys-slow-sql） | 超过 admintem.sql.slow-ms（默认 2000ms）WARN |

- **全链路 traceId**：`RequestTraceFilter`（config/log/FilterConfig 注册）为每个请求生成
  traceId 写入 MDC（日志行 `[traceId]`）与响应头 `X-Trace-Id`；接口日志与 SQL 日志同串可查；
- **SQL 日志**：`config/mybatis/SqlLogInnerInterceptor`（MyBatis-Plus InnerInterceptor，
  打印 mapperId + 可执行 SQL，修复了参考实现 Date 打印缺陷）；
- **SQL 日志脱敏（本轮加固）**：全量 SQL 会把参数值写入文件，其中可能含手机号/邮箱/证件号/口令。
  拦截器按"参数名关键字优先 + 值特征兜底"脱敏后再拼接：
  `password/pwd/secret/token` 类整体打码为 `***`；`phone/mobile/email/idcard/cardno` 类按类型脱敏
  （`139****5678`、`z***@example.com`、`110101********1234`）；**其余字段名也按值特征兜底**，
  避免敏感值因列名未命中关键字而漏网。开关 `admintem.sql.mask-enable`（默认 true，联调同样建议开启）；
  脱敏规则有单元测试锁定（`SqlLogMaskTest`，10 项）；
- **慢 SQL**：`config/mybatis/SqlSlowInterceptor`（MyBatis Executor 插件，update/query 计时，
  超阈值输出 WARN 到独立文件；配置 `admintem.sql.log-enable`（生产 false）与 `admintem.sql.slow-ms`）；
- **慢 SQL 阈值分级（本轮加固）**：`admintem.sql.slow-ms-by-mapper` 支持按 Mapper 名/方法名前缀
  设置更严格的阈值（最长包含匹配，未命中用默认值），用于"热路径收紧、重查询放宽"。
  日志行会打印实际生效的阈值（`慢SQL(>1000ms)`），便于判断命中哪一级。
  实测：默认配置下跑完整 67 项回归 + 冷启动，仅产生 1 条慢日志（首次登录 1794ms），
  说明分级阈值把噪声压住的同时保留了热路径可见性；
- **写入异步**：AsyncAppender 包装主要文件（discardingThreshold=0 不丢日志、queueSize 102400、
  maxFlushTime 1000ms、neverBlock=false），参考原项目 AsyncAppender 参数；
- **接口审计**：`RequestTraceFilter` 请求起止 + `ApiLogAspect` controller 层
  `类.方法、结果码、耗时`（不打印敏感参数与令牌，开关 `admintem.log.aspect.enable`）；
- 业务层：登录/注册/变更类操作均打印关键上下文日志（审计友好）。

## 7. 安全与健壮性清单

- BCrypt 存密码；校验参数（jakarta.validation）；
- 全局异常统一（业务码 + HTTP 401/403/404/405/500；非法 JSON/参数类型/唯一键冲突均已映射为 400）；
- 分页上限 500（`@Valid` 生效，pageNum/pageSize 空值有兜底）；
- **CORS 由配置驱动**（`admintem.security.cors-allowed-origins`）：dev/test/pre 默认放行本机端口，
  生产留空即不放开任何跨域来源（推荐 Nginx 同源反代）；
- **生产关闭接口文档**：pro profile 下 `springdoc.api-docs/swagger-ui.enabled=false`；
- 无状态会话；关闭 CSRF；JWT 密钥启动期校验（缺失或不足 32 字节直接启动失败）；
- SQL 层逻辑删除统一由 Mapper XML 显式维护，多表操作加 `@Transactional`；
- 权限变化即时清缓存（Redis 主动失效 + TTL 兜底）。

## 8. 页面级动态路由（已实现）与后续扩展点

### 8.1 页面级动态路由（DB 驱动）

前端路由由后端菜单驱动注册（V1.0.2 起，见 `src/router/index.js`）：

- 固定路由仅 `/login /register /403` 与根布局；业务页面**不再静态注册**；
- 约定：`sys_auth_permission.component` = `src/views` 下相对路径（不含扩展名与
  前导斜杠，如 `userInfo/UserInfo`、`HomeView`）；
- 前端用 `import.meta.glob('../views/**/*.vue')` 建立“component → 懒加载组件”映射，
  会话加载后按 menus 叶子把有权限页面 `router.addRoute` 挂到 Root(Layout) 下，末尾以
  `/:pathMatch(.*)*` 兜底 404（无权限/不存在路径统一 404，不泄露资源）；
- **新增页面三要素**：① 在 `src/views` 放置组件；② 在权限管理登记菜单
  （type=0，menuUrl + component + permission_key）；③ 授权给角色。无需改路由表；
- 用户切换/刷新会话时由守卫自动清理并重建动态路由；
- 叶子识别：菜单节点由后端显式下发 `type=0`；前端同时兼容历史缺省 type
  （视为菜单），避免“无法进入页面/首页误跳 403”的问题。

## 9. 多环境切换与 Redisson

### 9.1 Maven Profile 切环境（沿用原项目机制）

原项目通过 Maven Profiles 注入 `env-flag` 并开启 resources 过滤，
`application.yml` 用占位符激活对应 `application-{profile}.yml`。本工程复刻：

| Profile | env-flag | 激活文件 | 端口 | 前端 mode |
| ---- | ---- | ---- | ---- | ---- |
| dev（默认） | dev | application-dev.yml | 8090 | development |
| test | test | application-test.yml | 8091 | test |
| pre | pre | application-pre.yml | 8092 | pre |
| pro | pro | application-pro.yml | 8093 | pro |

用法：`mvn -P test spring-boot:run`；打包同理（`-P pro -DskipTests package`）。
由于 Spring Boot parent 将 maven-resources 分隔符设为 `@..@`，
application.yml 使用 `@env-flag@` 占位符。pro 环境默认关闭自助注册
（`admintem.auth.register-enabled=false`），pre/pro 连接信息含 TODO 发布清单。

### 9.2 Redisson（沿用原项目 Redis 方案并统一客户端）

- 依赖 `org.redisson:redisson`（3.52.0），不再引入 spring-boot-starter-data-redis；
- `config/RedissonConfig + RedissonProperties` 依据各环境 yml 顶层 `redisson:*`
  显式构建 `RedissonClient`（单机模式，随容器 shutdown）；
- Redis 访问统一改走 Redisson：
  - `JwtTokenService`：令牌白名单 `RBucket`（set + TTL / get / delete）；
  - `RbacCacheService`：权限快照 `RBucket`（JSON 读写与失效）；
  - `AuthServiceImpl`：登录失败计数 `RAtomicLong`（原子自增 + 过期）、锁定 `RBucket`。
- 键前缀仍为 `admintem:auth:*`（与旧项目 `security:jwt:*` 隔离）。

**Redis 序列化说明（已核查修复）**：全部缓存值使用 Redisson `RBucket<String>` 存取
“显式 JSON/普通字符串”，不经过 Spring Data Redis 的 JdkSerialization RedisTemplate，
因此不存在 key/value 序列化器歧义。此前发现并修复一个真实隐患：`LoginUser`
同时暴露 `getUsername()`（UserDetails）与 `getUserName()`，导致快照 JSON 出现
重复字段 `username`，读取时按“未知属性”失败、缓存永远未命中；修复方式：
- `LoginUser.getUsername()` 增加 `@JsonIgnore`（仅保留 `userName` 单字段）；
- 全局 `spring.jackson.deserialization.fail-on-unknown-properties: false` 兜底容错。
修复后快照（`{"userId":...,"userName":...,"roleKeys":[...],"permissionKeys":[...]}`）
可被稳定反序列化，缓存真正生效（未命中才回源数据库）。

## 11. 移动端设计（基础版）

移动端 `admintem-mobile` 与本系统是**同一个整体**：不新增任何后端接口，不新增权限标识，
仅作为同一套 RBAC 能力的另一个访问端。

| 维度 | 设计 | 理由 |
| ---- | ---- | ---- |
| 框架 | Vue 3.5 + Vite 8 + Pinia | 与桌面端同代，构建与状态管理范式一致 |
| UI 库 | Vant 4 | 面向触摸的移动组件库，标签栏/弹层/表单开箱即用 |
| 路由模式 | hash（`createWebHashHistory`） | 手机端常以静态托管/直接打开方式访问，免服务端 rewrite |
| 端口 | dev 5174 | 与桌面端 5173 并存，便于对照调试同一后端 |
| 令牌 | `localStorage.admintem_token` + 请求头 `admintem_token: "LAUNCH <jwt>"` | 与桌面端完全同构，后端无需区分端 |
| 会话 | `/auth/getUserInfo` 一次拉齐用户/角色/菜单/权限 | 与桌面端共用同一会话视图 `UserSessionVO` |
| 权限 | `v-perm` 指令按 `permission_key` 渲染管理入口 | 与后端 `@PreAuthorize`、桌面端 `v-perm` 同一标识 |
| 适配 | viewport 禁缩放 + `#app` 限宽 480px + 安全区内边距 | 手机全屏、电脑浏览器调试时居中呈现 |

页面与路由：

| 路由 | 页面 | 说明 |
| ---- | ---- | ---- |
| `#/login` | 登录 | 账号密码 + 记住我，登录后回跳 `redirect` |
| `#/home` | 首页 | 欢迎信息、数据概览（菜单/权限/角色数）、按权限渲染的管理入口、可访问菜单清单 |
| `#/mine` | 我的 | 资料与角色、账号信息、修改密码（改密后强制重登）、关于、退出登录（二次确认） |

守卫与失效处理：未知哈希回首页；未登录访问受保护页面跳登录并携带 `redirect`；
已登录但会话未加载（首次进入/刷新）先补拉会话，失败即清理令牌回登录页；
任何接口返回 401 由 axios 拦截器统一清理登录态并跳登录页。

范围边界：移动端**不承载**用户/角色/权限的完整管理界面，管理入口点击后明确提示
「请在桌面端使用」；后续扩展见《10-后续功能扩展规划》。

### 11.1 移动端专项加固（M1）

一轮针对"样式 / 代码 / 日志 / 注释"的专项检查，修掉 4 类问题：

| 类别 | 问题 | 处置 |
| ---- | ---- | ---- |
| 样式 | 两个阴影声明写法非法：`box-shadow: 0 0 0 1px var(--lc-frame-shadow)` 与 `box-shadow: 0 20px 40px -34px var(--lc-shadow-sheet)` —— 这两个 token **本身就是完整阴影值**，再拼前缀会让整条声明失效，表现为"阴影莫名其妙没了" | 改为整值引用 `box-shadow: var(--lc-frame-shadow)` / `var(--lc-shadow-sheet)`；并在 `check-tokens.cjs` 增加**永久规则**：阴影 token 只能整值使用，拼接即失败 |
| 样式 | 页面高度用 `100vh`：手机浏览器把地址栏算进视口，首屏会被挡住一截、滚动时跳动 | 统一 `min-height: 100vh` + `min-height: 100dvh`（保留旧内核回退） |

| 日志 | 请求失败只弹 Toast，没有结构化记录，线上无法定位 | `request.js` 统一记录方法/路径/状态码/traceId（不含令牌与请求体）；区分超时、网络不可达、4xx、5xx |
| 注释 | 模块注释总体齐全，`App.vue` 缺职责说明 | 补齐；新增 `logger.js` 带完整"为什么这样设计"说明 |

> 说明：`--lc-tap-min`（44px）与 `env(safe-area-inset-bottom)` 已在标签栏与页面底部留白中使用，
> 实测触摸目标最小 46px（按钮）/ 50px（标签项）/ 70px（管理入口），均达标。

## 12. 视觉语言与设计 token（纸面极简 · 编辑式）

### 12.1 为什么要有这一层

改造前的观感是"两套产品拼在一起"：登录/注册页自带一套纸面配色（写死的 `#15293f`、`#123c6e`…），
而所有管理页沿用 Element Plus 默认值（`#409eff` 主色、默认圆角与投影）。
统一主色需要改十几个文件，且极易漏改；移动端又是第三套数值。

因此 E 组改版刻意分成两步走，**顺序本身就是设计**：

1. **先收拢（E1）**：把散落的数值抽成两端各一份 `tokens.css`，此步承诺**零视觉变化**，
   并用"18/19 页像素完全一致"验证（唯一差异是时间相关的问候语）；
2. **再改视觉（E2–E8）**：每步都给出客观断言（计算样式、几何、对比度）与截图比对，
   主观观感交由人工评审——这样"改坏了"能立刻定位到是哪一步引入的。

### 12.2 设计语言四条

| 原则 | 具体做法 |
| ---- | ---- |
| 纸面与墨色 | 底色是极浅纸面 `#f5f6f8`（含 28px 极淡网格），卡片纯白；文字只用墨蓝色阶，不用纯黑 |
| 细线代替阴影 | 区域划分依靠 1px 细线（`#e6e9ef` / `#eef0f4`）；全站只保留一种极浅投影（卡片/弹层） |
| 编辑式排版 | 小标签（kicker，11px + 字距 2.4px 大写）+ 标题 + 一行口径说明，构成页面信息区 |
| 克制动效 | 只保留两类：页面/弹层入场（0.35–0.4s 上移淡入）与交互相应（0.15–0.18s 过渡） |

### 12.2.1 外壳间距（内容区与三面的距离）

登录后的所有菜单页面共用同一外壳 `layout/Layout.vue`，内容区与「左侧导航 / 顶栏 / 右侧窗口边」
的距离由 `.layout-main` 的 `padding` **单点控制**：

| 时间 | 取值 | 说明 |
| ---- | ---- | ---- |
| 2026-10 之前 | `var(--lc-sp-6)` = 24px | 页面自身已有 20px 内边距，外层再留 24px 形成"双层留白"，内容像被挤在中间一小块 |
| 2026-10-18 起 | **1px** | 按需求收紧到几乎贴合：内容卡片占满导航与窗口之间的区域，页面自己的 20px 内边距负责呼吸感 |

> 调大/调小只改这一个值（例如 4px / `var(--lc-sp-1)` / `var(--lc-sp-2)`），
> **不要在各页面分别加 padding**——那样会重新变成"每页间距不一致"。
> 实测（1440×900）：左 1px、上 1px、右 1px、无横向溢出；123 项设计层断言与 21 项桌面 E2E 全通过。

### 12.3 文件与职责（唯一出处）

### 12.5 组件库映射的两个作用域陷阱（已踩过）

1. **Element Plus 会在组件根类上定义自己的变量**（如 `.el-card { --el-card-border-color }`），
   组件作用域的声明优先于 `:root`，因此只写 `:root` 映射会出现"改了不生效"。
   处理：配色变量写到 `.el-table` / `.el-card` 作用域（见 `components.css` 注释）。
2. **Vant 同理**：`.van-field` 自己定义了 `--van-field-placeholder-text-color`，
   只映射 `:root` 会退回库默认值。处理：写在 `.van-field` 作用域并提升特异性（见移动端 `theme.css` 注释）。

## 13. 操作审计（sys_auth_audit_log）

### 13.1 为什么需要独立审计表

改造前的"操作留痕"分散在三处，都不能作为审计依据：

| 现有留痕 | 局限 |
| ---- | ---- |
| 应用日志（logs/admintem-info.log） | 按天滚动、会被清理，且非结构化，无法按人/对象检索 |
| 慢 SQL 日志 | 只关心性能，不关心"谁做了什么" |
| 业务表 `created_by` / `update_by` | 只能回答"最后一次是谁改的"，看不到"谁在什么时候移除的、当时成功还是失败" |

权限系统的治理诉求更明确：**"改权限的行为必须可追溯"**——某角色被移除某菜单后，
要能查到哪次操作、由谁执行、结果如何（包含被拒绝的尝试）。因此新增独立审计表。

### 13.2 落库范围与写入点

| 写入点 | 覆盖的动作 | 实现 |
| ---- | ---- | ---- |
| `@AuditLog` 注解 + `AuditLogAspect` | 登录、注册、登出、改本人资料/密码；用户 5 项、角色 4 项、权限 3 项增删改与授权（共 17 个动作） | 环绕通知，`finally` 中记录，成功/业务失败/抛异常都记一条 |
| `GlobalExceptionHandler`（方法级 403） | 按钮权限不足被拒绝的尝试 | 写 `ACCESS_DENIED` 记录 |
| `RestAccessDeniedHandler`（过滤器链 403） | 路径级规则拒绝的尝试 | 同上 |

> 为什么越权要单独记：`@PreAuthorize` 在方法调用**之前**就拒绝了，业务方法从未执行，
> 注解切面看不到这次请求；而"谁尝试了无权操作"恰恰是审计里最有价值的信号。

### 13.2.1 写入方式：异步（独立线程池）

审计落库放在独立线程池（bean \uditExecutor\：1 线程、队列 2000、\CallerRunsPolicy\）：
业务响应不再等待一次 DB round-trip；队列满时由调用线程自己执行，**宁可慢一点也不丢审计**；
停机时等待队列排空（最多 10 秒）。记录对象的构造仍在请求线程完成（需要
\HttpServletRequest\ 与登录上下文），只有"落库"这一步异步。
MDC 里的 \	raceId\ 通过 \TaskDecorator\ 传递，审计日志仍能与接口日志、SQL 日志对齐。

### 13.2.2 查询入口（V1.0.7）

审计此前只写不读，运维只能连库。现在提供只读查询：

| 接口 | 权限标识 | 说明 |
| ---- | ---- | ---- |
| `POST /sysAuthAuditLog/paginQuery` | `sysAuthAuditLog:paginQuery` | 按操作人 / 动作 / 目标名称 / 结果 / 时间范围分页；排序固定"时间倒序 + id 倒序" |
| `POST /sysAuthAuditLog/queryActions` | 同上 | 动作字典（动作码 + 中文名 + 出现次数），供筛选下拉 |

页面入口：菜单 `auditLog:auditLog`（`/auditLog`，组件 `auditLog/index`）。
查询条件与索引一一对应（`operator` / `action` / `created_time` 均有联合索引），
操作人、目标名用**前缀匹配**而不是 `%x%`，避免全表扫描。
明细抽屉展示请求路径、失败原因与 `traceId`，可直接拿去检索应用日志。

### 13.3 三条工程约束（审计是附加动作，不能影响主流程）

1. **失败不外抛**：审计写库异常在最靠近持久化的一层被吸收，只打 WARN 日志——
   否则"表不存在/字段超长"会让用户的正常操作失败，这与审计的定位相反；
2. **异常原样上抛**：切面记录后把业务异常原样抛出，不改写返回值、不吞异常；
3. **入库前归一**：按列宽截断文本、补齐时间与结果默认值，把"插入失败"变成"截断成功"。

这三条都有对应单测（`AuditLogAspectTest` / `AuditLogServiceImplTest`），
其中"审计服务抛异常时业务仍正常返回"是显式断言。

### 13.4 字段口径（几个刻意的选择）

| 字段 | 口径 | 原因 |
| ---- | ---- | ---- |
| `operator` | 已登录取登录账号；登录/注册这类匿名动作取**被尝试的账号** | 否则登录审计的操作人只能是 anonymous，失去意义 |
| `target_id` | 优先取入参 ID；新增类动作取**返回值里的新 ID** | 新增对象的 ID 调用前不存在，只在 `Result<Long>` 里 |
| `target_name` | 尽力从入参取（账号/角色名/权限名）；删除类动作可能为空 | 请求体只有 ID；不做额外回查，避免为填字段引入新失败点 |
| `request_uri` | 只记路径，不含查询串 | 避免把令牌/密码之类参数写进库 |
| `trace_id` | 取自 MDC，与请求日志、SQL 日志同值 | 一次请求的"接口 + SQL + 审计"可整体串联 |
| `client_ip` | 优先 `X-Forwarded-For` 首跳，其次 `X-Real-IP`，最后 `remoteAddr` | 反代场景下才能拿到真实来源 |

### 13.5 开关、运维与边界

| 项 | 说明 |
| ---- | ---- |
| `admintem.audit.enable` | 总开关（默认 true）。**只在持久化边界判断一次**，避免"切面关了但 403 出口还在写"的半开状态 |
| `admintem.audit.log-denied` | 是否记录 403 尝试（默认 true）；被安全扫描器刷 403 时可先关它降噪 |
| `admintem.audit.max-text-length` | 失败原因入库截断长度（默认 200） |
| `admintem.audit.retention-days` | 保留天数（默认 180）。程序**不做自动删除**：审计数据的清理应由运维显式执行，见《04》 |
| 已知边界 | ① 只覆盖被注解的动作与 403 出口，查询类动作不记（量太大且无治理价值）；② 不做自动归档；③ 审计查询页面/接口尚未提供，当前用 SQL 查询，规划见《10》 |
