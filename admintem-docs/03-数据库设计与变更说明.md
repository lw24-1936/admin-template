# 03-数据库设计与变更说明

## 1. 总原则

本工程**完全沿用旧项目 MySQL 库 `admintem_new`**，不重建库、不改动任何存量表结构与数据，
只做**增量、幂等、可回滚说明**的变更，变更脚本统一存放于：

```
admintem-docs/db/changelog/   （已应用脚本 + 新脚本按版本顺序存放）
```

Redis 沿用旧实例（database 0），键前缀隔离见《02-系统设计文档》第 5 节。

## 2. 现有表结构（沿用，未修改）

| 表 | 说明 | 关键列 |
| ---- | ---- | ---- |
| `sys_auth_user` | 用户 | user_name/nick_name/password(BCrypt)/status/is_deleted |
| `sys_auth_role` | 角色 | role_name/role_key/is_deleted |
| `sys_auth_permission` | 菜单+按钮 | type(0菜单 1按钮)/menu_url/component/backend_url/status/`show`/icon/permission_key/is_deleted |
| `sys_auth_user_role` | 用户-角色关联 | user_id/role_id/is_deleted |
| `sys_auth_role_permission` | 角色-权限关联 | role_id/permission_id/is_deleted |

> 注意：`admintem_new` 中原本存在的 `sys_auth_role_permission` 孤儿关联
> （permission_id=7..11，早期从 rand-system 拷贝历史遗留）本工程**未删除**；
> V1.0.1 新权限落库后恰好补全了这些 ID 指向的真实按钮（新增用户/编辑用户/删除用户/
> 重置密码/分配角色），关联即恢复有效语义，未做任何覆盖。

### V1.0.3 —— 菜单 status / show 字段归一（让两个字段真正生效）

脚本：`db/changelog/V1.0.3__align_menu_status_show.sql`（已应用，幂等可重放）

背景：`sys_auth_permission` 的列注释与前端「权限管理」界面都声明了这两个字段的语义——
`status`：0 启用 / 1 禁用(null 按启用)；`show`：0 展示 / 1 隐藏——但基线数据里 5 个菜单的
`show` 全为 1（按注释即"隐藏"）、3~5 号菜单 `status` 为 NULL，且代码此前并未读取这两个字段，
于是"隐藏/禁用"设置形同不存在，数据与注释互相矛盾。

变更内容与配套处置：

| 位置 | 处置 |
| ---- | ---- |
| 数据 | 5 个菜单统一为 `status=0`（启用）、`show=0`（展示）——与修正前的实际界面表现完全一致 |
| 后端 | 会话菜单树构建时过滤 `status=1`（禁用）的菜单：不下发，页面不可访问 |
| 前端（桌面端 / 移动端） | 按 `show=1` 在导航与菜单清单中隐藏；**隐藏菜单仍注册路由，可直接用 URL 访问** |
| 文档 | 本节 + 《05-接口与权限标识对照表》第 7 节 + 《06-测试报告》第 4.2 节 |

回滚：`UPDATE sys_auth_permission SET show=1, status=NULL WHERE type=0 AND id BETWEEN 3 AND 5;`
`UPDATE sys_auth_permission SET show=1 WHERE type=0 AND id IN (1,2);`

语义速查（新增/调整菜单时按此判断）：

| 需求 | status | show |
| ---- | ---- | ---- |
| 正常菜单 | 0 | 0 |
| 暂不开放的页面（连直达也禁止） | 1 | — |
| 隐藏菜单（不在导航显示，但可直达，如详情页） | 0 | 1 |

### V1.0.4 —— 热查询索引补齐

脚本：`db/changelog/V1.0.4__add_hot_query_indexes.sql`（已应用，幂等可重放）

背景（优化清单 B 组执行时发现）：`role_key`、`permission_key` 上没有索引，
两张关联表也只有"以 user_id / role_id 为前导列"的复合索引，导致四类热查询全表扫描。

| 索引 | 表(列) | 支撑的查询 |
| ---- | ---- | ---- |
| `idx_role_key` | sys_auth_role(role_key) | 登录判定超级角色、注册取默认角色、角色标识唯一性校验、会话构建 `selectByRoleKeys` |
| `idx_permission_key` | sys_auth_permission(permission_key) | 权限标识唯一性校验、会话构建 `selectByKeys` |
| `idx_role_id` | sys_auth_user_role(role_id) | 删除角色前绑定校验 `countByRoleId`、权限变更后按角色失效缓存 |
| `idx_permission_id` | sys_auth_role_permission(permission_id) | 删除权限时级联清理关联 `selectByPermissionIds` |

实测（EXPLAIN）：四类查询均由 `type=ALL / possible_keys=NULL` 变为
`type=ref` 且 `key` 命中上述新索引。

说明：索引保持**非唯一**（与既有 `idx_user_name` 约定一致），唯一性仍由应用层
`countByXxx`（排除自身）保证——这样逻辑删除后同名重建不会被唯一键挡住；
一键初始化脚本 `db/init/00_admintem_full_init.sql` 的建表语句已同步包含这 4 个索引。

### V1.0.5 —— 操作审计日志表

脚本：`db/changelog/V1.0.5__add_audit_log.sql`（已应用，幂等可重放）

背景：改造前的"操作留痕"分散在三处，都不足以作为审计依据——
应用日志按天滚动会被清理、慢 SQL 日志只关心性能、业务表的 `created_by/update_by`
只能回答"最后一次是谁改的"。权限系统尤其需要"改权限的行为可追溯"，
因此新增独立审计表。

| 项 | 说明 |
| ---- | ---- |
| 表名 | `sys_auth_audit_log`（新增，不改动任何既有表） |
| 写入时机 | ① 被 `@AuditLog` 注解的控制器方法执行完成（成功/业务失败/抛异常都记一条）；② 两处 403 出口（过滤器链 `AccessDeniedHandler`、方法级 `@PreAuthorize` 的异常处理器） |
| 表设计 | **只追加**：无 `is_deleted` 字段，Mapper 只提供 `insert`，避免审计记录被业务改写 |
| 关键字段 | `operator/operator_id`（操作人）、`action/action_name`（动作码与中文名）、`target_type/target_id/target_name`（操作对象）、`result/error_code/error_msg`（结果）、`client_ip`、`trace_id`、`cost_ms`、`created_time` |
| 索引 | `idx_audit_operator_time(operator, created_time)`、`idx_audit_action_time(action, created_time)`、`idx_audit_created_time(created_time)`、`idx_audit_trace(trace_id)`——对应四种审计查法 |
| 开关 | `admintem.audit.enable`（总开关）、`admintem.audit.log-denied`（是否记录 403 尝试）、`max-text-length`（失败原因截断）、`retention-days`（保留天数，仅运维清理用） |
| 影响面 | 无接口变更、无权限标识新增、前端无需改动；审计写入失败只告警、不影响业务 |
| 一键初始化 | `db/init/00_admintem_full_init.sql` 已同步该表（脚本语义为"重置到演示基线"，会一并清空审计表） |

### V1.0.6 —— 未删除行唯一索引（并发唯一性兜底）

脚本：`db/changelog/V1.0.6__add_active_unique_indexes.sql`（已应用，幂等可重放）

背景：`user_name` / `role_key` / `permission_key` 的唯一性原先**只靠应用层**
（Service 里"先 count 再 insert"），而三张表都只有普通索引。并发下两个请求可以同时通过
count 校验并双双插入成功，表里出现两个同名账号；登录查询 `selectByUserName` 走 `LIMIT 1`，
身份会随机落到其中一行，权限随之错乱。这是"业务上必须唯一"与"数据库没有约束"之间的缺口。

| 项 | 说明 |
| ---- | ---- |
| 新增索引 | `sys_auth_user.uk_user_name_active`、`sys_auth_role.uk_role_key_active`、`sys_auth_permission.uk_permission_key_active` |
| 索引形式 | **函数索引**：`UNIQUE KEY ... ((IF(is_deleted = 0, 业务键, NULL)))` |
| 为什么用函数索引 | 本系统逻辑删除（`is_deleted`）。普通唯一索引会把已删除行也算进去，导致"删掉后无法用同名重建"；函数索引把已删除行的表达式求值为 `NULL`，而 MySQL 唯一索引允许多个 `NULL`，于是"未删除行唯一 + 已删除行可同名共存"两条需求同时满足 |
| 应用层配合 | 保留 count 校验（为了友好提示与明确业务码）；同时把 `insert` 的 `DuplicateKeyException` 转成同一业务码（用户 505、角色/权限 400+具体提示），并发与串行两条路径对外表现一致 |
| 执行前检查 | 脚本开头会输出重复数据（正常为空）；若真有重复，`ALTER` 会失败并报 `Duplicate entry`——这是期望行为，宁可失败也不要静默放过 |
| 影响面 | 无接口/字段变更；插入性能影响可忽略（唯一索引与普通索引同为 B+Tree 维护） |
| 一键初始化 | `db/init/00_admintem_full_init.sql` 的三张表建表语句已包含这三个唯一索引 |

> 顺带把一键初始化脚本改成**必须显式确认**才执行（`SET @admintem_confirm_reset = 1`），
> 未确认时 `SIGNAL` 中止且不删除任何表。原因见《09》第 18 节的一次真实事故记录。

审计字段口径（实测样例见《06-测试报告》）：登录类动作的操作人取**被尝试的账号**
（登录时尚未认证）；新增类动作的目标 ID 取自返回值（新对象 ID 只在返回值里）；
删除/分配类动作的请求体只有 ID，因此 `target_id` 有值而 `target_name` 可能为空——
审计只记录"请求确实携带的信息"，不做额外回查，避免为了填名字而引入新的耦合与失败点。

```bash

    sys_auth_user_role sys_auth_role_permission > admintem_new_rbac_backup.sql
```

### V1.0.4 —— 热查询索引补齐

脚本：`db/changelog/V1.0.4__add_hot_query_indexes.sql`（已应用，幂等可重放）

背景（优化清单 B 组执行时发现）：`role_key`、`permission_key` 上没有索引，
两张关联表也只有"以 user_id / role_id 为前导列"的复合索引，导致四类热查询全表扫描。

| 索引 | 表(列) | 支撑的查询 |
| ---- | ---- | ---- |
| `idx_role_key` | sys_auth_role(role_key) | 登录判定超级角色、注册取默认角色、角色标识唯一性校验、会话构建 `selectByRoleKeys` |
| `idx_permission_key` | sys_auth_permission(permission_key) | 权限标识唯一性校验、会话构建 `selectByKeys` |
| `idx_role_id` | sys_auth_user_role(role_id) | 删除角色前绑定校验 `countByRoleId`、权限变更后按角色失效缓存 |
| `idx_permission_id` | sys_auth_role_permission(permission_id) | 删除权限时级联清理关联 `selectByPermissionIds` |

实测（EXPLAIN）：四类查询均由 `type=ALL / possible_keys=NULL` 变为
`type=ref` 且 `key` 命中上述新索引。

说明：索引保持**非唯一**（与既有 `idx_user_name` 约定一致），唯一性仍由应用层
`countByXxx`（排除自身）保证——这样逻辑删除后同名重建不会被唯一键挡住；
一键初始化脚本 `db/init/00_admintem_full_init.sql` 的建表语句已同步包含这 4 个索引。

背景：改造前的"操作留痕"分散在三处，都不足以作为审计依据——
应用日志按天滚动会被清理、慢 SQL 日志只关心性能、业务表的 `created_by/update_by`

因此新增独立审计表。

| 项 | 说明 |

| 写入时机 | ① 被 `@AuditLog` 注解的控制器方法执行完成（成功/业务失败/抛异常都记一条）；② 两处 403 出口（过滤器链 `AccessDeniedHandler`、方法级 `@PreAuthorize` 的异常处理器） |

### V1.0.6 —— 未删除行唯一索引（并发唯一性兜底）

脚本：`db/changelog/V1.0.6__add_active_unique_indexes.sql`（已应用，幂等可重放）

背景：`user_name` / `role_key` / `permission_key` 的唯一性原先**只靠应用层**
（Service 里"先 count 再 insert"），而三张表都只有普通索引。并发下两个请求可以同时通过
count 校验并双双插入成功，表里出现两个同名账号；登录查询 `selectByUserName` 走 `LIMIT 1`，
身份会随机落到其中一行，权限随之错乱。这是"业务上必须唯一"与"数据库没有约束"之间的缺口。

| 项 | 说明 |
| ---- | ---- |
| 新增索引 | `sys_auth_user.uk_user_name_active`、`sys_auth_role.uk_role_key_active`、`sys_auth_permission.uk_permission_key_active` |
| 索引形式 | **函数索引**：`UNIQUE KEY ... ((IF(is_deleted = 0, 业务键, NULL)))` |
| 为什么用函数索引 | 本系统逻辑删除（`is_deleted`）。普通唯一索引会把已删除行也算进去，导致"删掉后无法用同名重建"；函数索引把已删除行的表达式求值为 `NULL`，而 MySQL 唯一索引允许多个 `NULL`，于是"未删除行唯一 + 已删除行可同名共存"两条需求同时满足 |
| 应用层配合 | 保留 count 校验（为了友好提示与明确业务码）；同时把 `insert` 的 `DuplicateKeyException` 转成同一业务码（用户 505、角色/权限 400+具体提示），并发与串行两条路径对外表现一致 |
| 执行前检查 | 脚本开头会输出重复数据（正常为空）；若真有重复，`ALTER` 会失败并报 `Duplicate entry`——这是期望行为，宁可失败也不要静默放过 |
| 影响面 | 无接口/字段变更；插入性能影响可忽略（唯一索引与普通索引同为 B+Tree 维护） |
| 一键初始化 | `db/init/00_admintem_full_init.sql` 的三张表建表语句已包含这三个唯一索引 |

> 顺带把一键初始化脚本改成**必须显式确认**才执行（`SET @admintem_confirm_reset = 1`），
> 未确认时 `SIGNAL` 中止且不删除任何表。原因见《09》第 18 节的一次真实事故记录。

审计字段口径（实测样例见《06-测试报告》）：登录类动作的操作人取**被尝试的账号**
（登录时尚未认证）；新增类动作的目标 ID 取自返回值（新对象 ID 只在返回值里）；
删除/分配类动作的请求体只有 ID，因此 `target_id` 有值而 `target_name` 可能为空——
审计只记录"请求确实携带的信息"，不做额外回查，避免为了填名字而引入新的耦合与失败点。

### V1.0.10 —— 修正内置 admin 手机号

脚本：`db/changelog/V1.0.10__fix_admin_phone.sql`（幂等）

**背景**：种子数据里 admin 的手机号写成 12 位（`121345678908`），而
`UpdateProfileRequest.phone` 的校验是 `^$|^1\d{10}$`。
结果是管理员打开「个人资料」只要提交就会 400 —— 页面看起来正常，保存一直失败。

**处理**：
- 初始化脚本 `00_admintem_full_init.sql` 改为 `12134567890`；
- 增量脚本只更新"仍是旧值"的行，不覆盖用户自己改过的号码；
- 不涉及表结构变更，可安全重放。

**验证**：修正后 `admin` 的资料保存 200，手机号回显 11 位。

### V1.0.11 —— 角色数据范围（行级数据权限）

脚本：`db/changelog/V1.0.11__add_role_data_scope.sql`（只新增列，不重放历史数据）

**背景**：原权限模型只覆盖"能不能进页面/能不能点按钮"，无法约束同一页面看到哪些行数据。

**处理**：
- `sys_auth_role` 新增 `data_scope`，取值 `ALL / DEPT / DEPT_AND_CHILD / SELF`，默认 `ALL`；
- 已有角色升级后保持全量数据，行为不变；
- 用户列表按当前登录用户角色的最宽范围过滤；服务端计算条件，客户端不能伪造；
- 管理员角色（`admin`）始终为 `ALL`，避免把自己锁死。

**验证**：角色管理可配置数据范围；非管理员选择 `DEPT`/`DEPT_AND_CHILD`/`SELF` 后用户列表只返回对应部门/本人数据。

> 注意：为保持已发布迁移的 checksum 不变，`db/init` 的 `sys_auth_role` 不预置
> `data_scope` 列，由本迁移在首次启动时添加；只执行 init 不执行 Flyway 时表结构不完整。

### V1.0.14 —— 文件中心

脚本：`db/changelog/V1.0.14__add_sys_file.sql`

**内容**：
- 新增 `sys_file` 元数据表（原始名、URL、大小、MIME、存储策略、上传人）；
- 新增「文件中心」菜单与上传/删除按钮（35~37），自动授予 admin；
- 文件字节仍由 `StorageStrategy` 保存到 local/MinIO，元数据与物理文件分离；
- 默认白名单不包含可执行脚本；大小上限 `admintem.upload.file-max-size-mb=10`。

**安全边界**：当前本地文件位于公开 `/uploads` 目录，只适合公开附件/图片；合同、证件等敏感文件应改成鉴权下载接口。

**验证**：上传 txt 成功并写入元数据；列表可见；删除后逻辑删除并清理物理文件。
