# 08-权限“动态认证”实现与原项目对比

> 说明：原项目指 `demo/RandomSelectionSystem`（Spring Boot 2.4.2 + Spring Security 5）。
> 本文对比两者“动态权限判定”的落地方式，说明新工程为何采用 permission_key + 注解式动态鉴权。

## 1. 原项目：URL 级动态授权（access 表达式 + 每次查库）

### 1.1 配置方式

```java
// SpringSecurityConfig（旧）
.authorizeRequests()
    .antMatchers(ignores).permitAll()            // 白名单
    .anyRequest()
    .access("@rbacAuthorityService.hasPermission(request,authentication)") // 每个请求都走 Bean 判定
```

### 1.2 判定逻辑（RbacAuthorityService）

1. `checkRequest(request)`：从 `RequestMappingHandlerMapping` 收集全部注册接口
   （URI → HTTP 方法集合），先确认“当前请求是一个真实接口”；
2. 用户角色含 `role_key = admin` → 直接放行；
3. 否则从数据库实时加载该用户的角色与权限
   （`selectUserWithRolesAndPermissions`），逐个权限取其
   `backend_url`，用 `AntPathRequestMatcher(backendUrl)` 匹配当前请求 URI，命中即放行。

### 1.3 特征

| 维度 | 旧实现表现 |
| ---- | ---- |
| 权限载体 | 以 `backend_url`（URL 路径）为授权对象，permission_key 主要用于前端菜单勾选 |
| 判定位置 | Security 过滤器链内的 `access` 表达式，覆盖 `anyRequest` |
| 数据来源 | **每次请求实时查库**（含角色与权限多级关联） |
| 方法与 URL 是否对应 | URL 匹配不区分权限记录的语义（“按钮/接口”粒度依赖每行一条 backend_url） |
| 按钮级 | 受限于 URL 粒度，页面内多个操作共用一个 URL 时无法区分 |
| 优点 | 增删接口只要在库里配好 URL 即可生效，无需改代码注解 |

## 2. 新工程：permission_key + 方法级注解 + Redis 快照

### 2.1 关键组成

- **契约统一**：`sys_auth_permission.permission_key` 同时被三处引用：
  ① 前端 `v-perm` 指令（控制按钮显隐）、② 前端路由守卫 `meta.perm`（控制页面）、
  ③ 后端 `@PreAuthorize("@rbac.hasPerm('xxx')")`（最终安全边界）。
- **判定链路（请求级）**：
  1. `JwtAuthenticationFilter`：验签 → Redis 白名单 → 从 Redis 快照
     （`admintem:auth:user:perm:{userId}`）恢复 `LoginUser`（未命中回源 DB 并回填）；
  2. Spring Security 方法级安全（`@EnableMethodSecurity`）调用
     `RbacService.hasPerm(key)`：
     - 拥有 `role_key = admin`（可配置）→ 放行；
     - 否则 `LoginUser.permissionKeys.contains(key)`；
  3. 接口一旦没有对应注解 key，只有“已登录”才可访问（登录接口本身白名单）。
- **权限缓存一致性**：角色/权限/用户变更时，主动按“角色 → 用户”反查并清空受影响用户的
  Redis 快照；另有 30 分钟 TTL 兜底，避免长期陈旧。
- **逻辑删除与数据**：见《02-系统设计文档》；持久层 SQL 全部 XML 显式维护。

### 2.2 特征

| 维度 | 新实现表现 |
| ---- | ---- |
| 权限载体 | 以 `permission_key`（字符串语义标识）为唯一授权契约 |
| 判定位置 | 方法级（精确到每个 Controller 方法） |
| 数据来源 | 登录后 Redis 快照，变更即时失效；**不每次请求查库** |
| 按钮级 | 一个按钮 = 一条 type=1 权限 = 一个 key = 前端按钮 + 后端方法，粒度精确 |
| 页面级 | 菜单 key 控制路由与侧边栏（前端） |
| 优点 | 前端/后端一套 key 不会漂移；鉴权靠近业务方法；性能好（缓存） |

## 3. 对比结论表

| 对比项 | 原项目（Spring Boot2） | 本工程（Spring Boot3.5） |
| ---- | ---- | ---- |
| 授权对象 | backend_url（URL） | permission_key（语义 key） |
| 动态判定入口 | `anyRequest().access(...)` | `@PreAuthorize("@rbac.hasPerm(key)")` + `anyRequest().authenticated()` |
| 数据加载 | 每次请求查库 | Redis 快照 + DB 回源 + 主动失效 |
| URL/方法区分 | AntPathMatcher 不区分 HTTP 方法 | 注解精确绑定方法，天然区分 GET/POST |
| 按钮级权限 | 无（同 URL 不可区分） | 有（按钮 = key，前后端一致） |
| 白名单 | antMatchers(ignores) | requestMatchers(permitUrls + swagger) |
| 未登录/无权限响应 | JSON（401/403） | JSON（401/403，格式统一） |
| 变更生效 | 即时（每请求查库，代价高） | 授权/权限变更即时清缓存，下次请求生效 |
| 向后兼容 | —— | DB 中 `backend_url` 保留作展示/审计，迁移期可按 key 回查 URL |

## 4. 附：为什么保留 `backend_url` 字段

原库 `sys_auth_permission.backend_url` 用于旧版 URL 授权。新工程鉴权不再依赖它，
但**保留该列**（V1.0.1 种子已为每个按钮同步填写真实接口地址），价值：
- 权限树页面直观展示“按钮 → 接口”映射，方便核对；
- 若未来需要“URL 级兜底鉴权”或接口清单自动巡检，可直接复用该列。
